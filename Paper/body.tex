\hypertarget{introduction}{%
\section{Introduction}\label{introduction}}

Adding or removing a database node is not a single event. Membership
changes, replicas move, obsolete files are reclaimed, and clients
continue to issue operations while the storage engine reorganizes data.
A cluster can therefore appear stable in its topology metadata while
foreground performance or local disk activity remains unsettled.
Comparisons that report only operation latency or the return time of a
topology command can miss those distinctions.

ScyllaDB offers two data-distribution mechanisms within the same
database: vnode-based token ownership and table-specific tablets with
explicit replica placement \cite{r1,r6}. This makes it possible to
compare mechanisms while retaining the database implementation, schema,
replication factor and workload. However, their monitoring surfaces are
not interchangeable. A tablet replica-size observation, a vnode
ownership percentage, a stream-manager byte counter and an SSTable
partition estimate describe different quantities.

This paper addresses three questions. First, how do placement and
observed quiescence evolve through a complete expansion/contraction
lifecycle? Second, how do client scheduling, operation latency and
storage maintenance relate to those transitions? Third, which apparent
differences survive an audit of metric meaning, sampling and physical
storage contents?

The contribution is an event-aligned case study combining request logs,
continuous topology and resource observations, retained vnode server
logs, exact-build source inspection and an offline audit of preserved
SSTables. It reconstructs tablet placement inheritance, separates
topology quiescence from delayed service effects, and accounts exactly
for an apparent excess of physical replicas. These complementary
outcomes provide a baseline for studying scaling mechanisms under
constrained resources.

\hypertarget{background-and-related-work}{%
\section{Background and related
work}\label{background-and-related-work}}

Dynamo's consistent-hashing design assigns multiple virtual positions to
physical nodes to support incremental redistribution \cite{r24}. Apache
Cassandra's architecture documentation describes the balance and
operational tradeoffs of multiple tokens, including the larger set of
replica neighbors \cite{r29}. Equal token counts therefore need to be
distinguished from effective replicated ownership. Bigtable develops
tablets as independently managed row ranges \cite{r25}; ScyllaDB applies
table-specific partitioning to a replicated token space, with explicit
host and shard placement \cite{r1}.

ScyllaDB's implementation account describes tablets as units of
placement and storage organization, including per-tablet memtables and
SSTables, migration and cleanup \cite{r27}. Its Raft-topology account
explains the coordination of metadata changes through a fault-tolerant
topology coordinator \cite{r28}. These sources motivate inspecting both
range boundaries and replica assignments. They also clarify the
comparison: both treatments here run the same ScyllaDB build, so the
contrast concerns data distribution within ScyllaDB. Cassandra studies
provide context rather than an interchangeable implementation baseline.

Elasticity research evaluates the cost of changing capacity while
serving requests. Kuhlenkamp, Klems and Röss compare Cassandra and HBase
using both scaling speed and workload impact, and examine the
sensitivity of results to infrastructure and reproduction \cite{r30}.
Yamaguchi and Morimitsu identify disk I/O during Cassandra node joining
as a scaling bottleneck and investigate page-cache and I/O-scheduling
changes \cite{r31}. Their findings motivate examining storage work
alongside topology, without identifying the cause of an individual
slowdown in our environment. OnlineElastMan uses workload prediction and
a learned performance model to provision Cassandra storage under
changing load and response-time objectives \cite{r32}. Its proactive
control problem complements our fixed, externally triggered lifecycle,
which concentrates on explaining immediate and delayed effects.

YCSB supplies a configurable framework for cloud-serving evaluation
\cite{r26}. Our custom serial client instead preserves identical
operation/key sequences and records scheduled and actual starts, making
accumulated backlog directly auditable. Offline storage inspection adds
another perspective: ScyllaDB's partition-estimate path aggregates
SSTable estimates \cite{r21}, while repeated keys across files can
inflate the total relative to distinct replicas. Flushing persists
memtables while leaving other aspects of memory state intact \cite{r5}.
Accordingly, we analyze logical ownership, physical file overlap,
maintenance and client service as separate outcomes.

container hard-memory quota. Effective CPU frequency, storage throughput
and VM vCPU allocation were not recorded in the available primary
evidence.

The exact version and build ID match ScyllaDB's published x86-64
\textbf{release} entry \cite{r33}. The date/commit suffix identifies its
build; it does not identify a pre-release. Runtime developer mode is a
separate setting. The schema and LOCAL\_QUORUM settings follow
ScyllaDB's documented interfaces \cite{r2,r3}.

The treatments used fresh project-scoped volumes and distinct keyspaces.
Tablets ran first on 21 September 2026 and vnodes second on 22
September. Fixed container names and network addresses required
sequential execution. The dataset remained loaded through each
lifecycle, but workload phases were separated by checks, warmups and
operator delays. Thus the experiment maintained dataset continuity, not
uninterrupted mixed traffic across the entire day.

RF=2 preserves nontrivial replica-placement choices in a three-node
baseline. The one-rack tablet configuration does not satisfy ScyllaDB's
RF-rack-valid terminology \cite{r10}, and a separate creation warning
reported RF below the recommended threshold of three. The configuration
permits the placement and streaming observations studied here; the
findings apply to this single-rack warning state. Rack-failure behavior
was outside the experiment.

The observed startup warnings also matter: the perf-event stall detector
fell back to a timer, SCHED\_FIFO scheduling was unavailable, memory was
approximately 974 MiB per shard, and the I/O scheduler was reported as
improperly configured. These deviations from recommended deployment
conditions affect the interpretation of performance \cite{r7}.

Every phase had a 30-second, read-only warmup at the same target rate.

\hypertarget{measurement-definitions}{%
\subsection{Measurement definitions}\label{measurement-definitions}}

\textbf{Client operation latency} is the monotonic elapsed time inside
the workload's operation boundary. That boundary includes client-side
value generation, the driver call, read validation or
expected-write-state handling. It is not isolated server execution time.

\textbf{Scheduled-start lag} is actual monotonic start offset minus
scheduled offset. The client is serial: when operation time and
intervening work exceed the two-millisecond average budget, it
accumulates backlog and subsequently catches up. A target of 500/s
therefore does not mean an independent concurrent arrival process
delivered exactly 500 requests in every wall-clock second.

\textbf{Placement-and-counter quiescence onset} is the earliest saved
topology observation followed by at least 60 seconds of unchanged
placement and idle collected streaming counters, with complete required
groups. It is a retrospective metadata-and-counter milestone. It does
not measure all transfer paths, deferred compaction or sustained client
recovery. The full confirmation window becomes available only later;
collection cadence limits temporal resolution.

\textbf{Ownership} denotes logical token-space coverage.
\textbf{Replica-size bytes} describe reported tablet replica storage.
\textbf{SSTable entry counts} and \textbf{distinct local keys} are
separate measures. Gross Docker network and block I/O include other
traffic and storage work and are rounded cumulative values \cite{r12}.
Throughout, MB denotes decimal megabytes; MiB and GiB denote binary
units.

\hypertarget{instrumentation-and-analysis}{%
\subsection{Instrumentation and
analysis}\label{instrumentation-and-analysis}}

Tablet placement and size metadata were sampled approximately once per
second. Vnode ring commands ran approximately every two seconds,
retaining raw output, acquisition start/end times and SHA-256 hashes.
The documented incoming/outgoing stream-manager counters \cite{r11} were
collected per node, shard and direction at roughly one-second intervals.
Docker samples were typically three to four seconds apart. Event records
identified command starts, returns and process removal; separate health
checks recorded membership, tasks, streams, restarts and OOM flags.

Phase summaries use linear-interpolated quantiles at position
\texttt{(n-1)p}, rounded to three decimals. UTC timestamps align
independently recorded evidence; durations and scheduling conclusions
use monotonic fields. Appendix A contains clock, sampling and parser
validation details.

To investigate the final partition estimates reported by
\texttt{tablestats} \cite{r4}, we mounted preserved vnode volumes
read-only and used the matching \texttt{dump-statistics} and
\texttt{dump-data} tools \cite{r23}. File inventory and modification
times selected the 12 SSTables corresponding to the pre-shutdown
checkpoint. We compared metadata row counts with extracted keys,
deduplicated within each node and counted node membership for every key.
This retrospective audit tests whether apparent excess replicas arise
from local file overlap; its selected-file scope excludes later shutdown
files and memtables.

Each treatment completed 1.08 million measured operations with zero
reported failures, invalid IDs or index errors. The read/write counts
matched exactly by phase: 48,170/11,830; 360,305/89,695; 48,012/11,988;
360,268/89,732; and 48,084/11,916. Saved write-state checks found no
missing or mismatched latest seeds. Both final logical counts were
750,000; 500 written and 500 never-written sampled values per treatment
matched at LOCAL\_QUORUM. The value verification covers the measured
operations and sampled keys.

2.240 ms versus 3.033 ms for tablets, approximately \textbf{26.1\%

performance. Fixed run order, separate days, cache and maintenance
histories, and shared-host activity constrain comparisons from the
outset. Windows available memory later fell to 161 MiB during tablet
expansion; the available evidence cannot isolate its effect. Phase
differences below are descriptive observations of these histories.

\hypertarget{tablet-splitting-merging-and-placement-inheritance}{%
\subsection{Tablet splitting, merging and placement
inheritance}\label{tablet-splitting-merging-and-placement-inheritance}}

Figure~\ref{fig:topology} summarizes the observed
lifecycle. The saved metadata separates a change in range boundaries
from a change in replica placement. All 32 original ranges split into
two children; each child pair had identical host/shard assignments.
Twenty-eight pairs matched the parent's current assignment in the
preceding snapshot, and four matched its pending assignment. Thus all 32
pairs were explained once migration state was included. Treating only
the old current assignment as authoritative would have created four
false anomalies.

During merging, all 32 final ranges combined two prior ranges.
Thirty-one pairs already had identical current host/shard assignments.
The apparent exception, ending at token -1, had a pending migration in
\texttt{use\_new} that aligned the second child with the first. The next
snapshot recorded the merged parent's aligned assignment. This resolves
the observed placement discrepancy without claiming that sampling
captured every internal step.

One sampled intra-node migration moved a replica from shard 0 to shard 1
on node 2, retaining the same two hosts. Its resulting placement matched
the neighboring merge partner. This is consistent with merge
preparation, although the internal scheduling decision was not logged.
After the range count had fallen to 32, a separate migration moved one
replica from node 1 to node 2 while retaining node 3. That
surviving-node reassignment explains why range-count convergence
preceded placement convergence.

The exact-build allocator defaults predict the observed 32/64/32
sequence from eligible shard counts \cite{r22}. Small observed replica
sizes favor this explanation over a data-size trigger; missing
historical runtime settings leave the attribution conditional (Appendix
B).

Across the complete lifecycle, the original 32 boundary positions
returned, but 11 ranges had different host sets and 12 had different
host/shard assignments. The aggregate node counts returned to 21/22/21.
Restoration of aggregate balance therefore did not mean restoration of
the original placement. By contrast, the initial and final vnode
token-owner signatures matched, with 768 tokens and 256 per surviving
node.

\hypertarget{discussion}{%
\section{Discussion}\label{discussion}}

\hypertarget{the-mechanisms-expose-different-notions-of-completion}{%
\subsection{The mechanisms expose different notions of
completion}\label{the-mechanisms-expose-different-notions-of-completion}}

The tablet lifecycle involved migration, shard alignment,
splitting/merging and subsequent redistribution. Its final boundary
count and aggregate replica counts returned to their initial values
while individual assignments changed. Vnode token ownership returned to
its original signature, but local storage contents still reflected
streaming and overlapping SSTables. Logical placement and physical file
organization therefore followed different histories even when the
cluster returned to three members.

The delayed vnode maintenance result also separates topology convergence
from service recovery. An unchanged ring and idle streaming counters
establish the specified quiescence condition, but do not imply that all
deferred storage work is finished. Conversely, a client can recover from
backlog by issuing requests faster than the target schedule for a
period, so a near-target phase average does not imply an undisturbed
transition.

\hypertarget{multiple-outcomes-and-scope}{%
\subsection{Multiple outcomes and
scope}\label{multiple-outcomes-and-scope}}

Tablets achieved equal four-node token-space shares and required no
manual post-join cleanup in this lifecycle. Vnodes reached the
placement-and-counter milestone earlier. Client backlog favored opposite
treatments in the two transition directions, while offline extraction
resolved the physical-count anomaly. Together these observations show
why an elasticity comparison benefits from several endpoints rather than
one completion time.

\textbf{Scope and limitations.} One lifecycle per treatment, fixed
order, unequal baselines and inter-phase gaps, and vnode-only cleanup
limit causal inference. Shared CPU, NVMe storage, filesystem cache and
host memory couple all processes; the 161-MiB Windows observation alone
cannot establish paging. Effective VM vCPU limits and exact configured
memory were unavailable. Vnode logs support a deferred-compaction
explanation, whereas the missing tablet logs leave its expansion
slowdown without a server-side diagnosis. Source inspection establishes
implementation-consistent mechanisms; historical runtime choices remain
conditional where settings were not retained. Sampled quiescence covers
only the recorded metadata and counters, and independent collector clock
offsets were not calibrated. The evidence thus supports a descriptive
single-host case study, with treatment-level repeatability and
production generalization left open.

\hypertarget{future-work}{%
\subsection{Future work}\label{future-work}}

Repeated, counterbalanced runs on multiple hosts would estimate
variability and separate treatment from execution history. Effective
runtime configuration and symmetric server logs would strengthen
mechanism attribution. Controlled maintenance and dedicated
transfer-path instrumentation could isolate deferred storage effects and
compare migration bytes on a common basis. Workload concurrency,
replication and dataset size are further dimensions for testing the
findings.

\hypertarget{conclusion}{%
\section{Conclusion}\label{conclusion}}

Two workload-matched ScyllaDB lifecycles completed 1.08 million requests 
each without reported workload failures and retained 750,000 logical keys.
Tablets adapted range boundaries and replica placement; vnodes restored
token ownership while retaining a different local file history. The main
distinction is the separation between placement quiescence, deferred
maintenance and client service: an early topology milestone can precede
a substantial later backlog.

The audit explains the observations at several levels. Pending
assignments reconcile tablet split/merge inheritance,
implementation-specific paths explain why stream counters cannot be
compared as total movement, and vnode logs associate deferred work with
a later slowdown. Exact offline key extraction accounts for all 72,501
excess final SSTable entries as overlap across files on the same node.
These findings establish a concrete baseline for deeper, replicated
studies of scaling behavior.
